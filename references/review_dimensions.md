# 笔记审查维度

笔记生成后**必须**进入审查阶段。审查不是走形式 —— 法考笔记的错误会直接被考生背进去，代价极高。

审查采用**多维度并行、互相独立**的方式：同一批笔记派多个 subagent，每个只盯一个维度。这样做有三个好处：

1. 每个 reviewer 的注意力集中，能发现"什么都看一点"时必然漏掉的深问题；
2. 维度之间天然交叉验证（法条维度说"规则写错了"，答案维度说"与正确答案矛盾"，两条独立证据指向同一处）；
3. 并行执行，耗时≈单个 reviewer。

## 六个审查维度

### D1 法条准确性（最高优先级）

**审查对象**：笔记里的法律规则、构成要件、期限、比例、机关权限。

**要抓的问题**：

- 规则表述错误或与现行法不一致（尤其是近年修法：民法典、刑诉法、行政处罚法、公司法、民诉法等）；
- 引用**已废止或已修改**的法条（如旧公司法条文、旧刑诉法期间）；
- 口诀/总结压缩过度导致含义失真（把"可以"写成"应当"、把"或"写成"且"）；
- 期限、比例、人数等数字类错误 —— 这是法考最高频的送分/送命点；
- 把"通说"当成唯一正确答案，或把存在争议的点写成定论。

**输出**：逐条列出「问题位置 → 错误内容 → 正确表述 → 依据 → 严重度」。

### D2 答案与解析一致性

**审查对象**：笔记结论 vs 原始数据里的 `correctAnswer` 与 `explanation`。

**要抓的问题**：

- 笔记里的结论与官方正确答案**矛盾**（最严重）；
- 笔记把某个**错误选项**的说法当作正确规则写进去（因为解析里常先复述错误观点再否定它，子代理可能摘错）；
- 笔记对某题的解析做了过度推论，超出了官方解析范围；
- 某题的正确答案被漏掉，导致该知识点结论不完整（如多选题只写了一个正确项）。

**方法**：reviewer 必须**回读该单元的原始 JSON**（`scrape/units/*.json`），逐题比对，不允许只看笔记。

### D3 知识点覆盖完整性

**要抓的问题**：

- 单元里有高频考点（同一知识点被 ≥3 题考到）但笔记未收录；
- 章节覆盖不全：某章节的题被整体忽略；
- 只写了"考什么"没写"怎么考"，导致复习时无法定位到选项层面的陷阱。

**输出**：列出漏掉的知识点 + 对应题号（questionId），让修订环节能补齐。

### D4 结构与格式合规

**要抓的问题**：

- 违反格式约束（出现代码块、HTML、图片、链接、脚注）—— 会直接破坏 PDF 渲染；
- 标题层级混乱（跳级、同一层级含义不一致）；
- 表格列数不一致或内容溢出（会引起 PDF 渲染错乱）；
- 该用表格的地方用了长段落（对比、期限、程序类）；
- 篇幅严重失衡（某知识点占了一半篇幅）。

### D5 学员适配（对齐 `study_profile.json`）

**要抓的问题**：

- 薄弱科目没有获得应有的篇幅倾斜；
- 复习轮次与内容不匹配（三轮冲刺的笔记里还在讲基础推导）；
- 距考天数 ≤30 天但笔记没有「优先掌握 Top 5」清单；
- 学习习惯是碎片时间，但笔记全是长段落、没口诀没表格。

### D6 跨单元去重与衔接

**要抓的问题**（需要把同科目的多个 part 一起看）：

- 相邻 part 重复讲同一知识点且结论不一致（合并后会"打架"）；
- 同一科目内编号体系、术语不统一（如一处"客观要件"一处"构成要件要素"）；
- 某 part 认为是重点、另一 part 认为是次要，优先级自相矛盾。

## 严重度分级

| 级别 | 含义 | 处理要求 |
|---|---|---|
| **P0** | 法律规则错误 / 与正确答案矛盾 —— 会把考生带错 | **必须修订**，修订后必须复审 |
| **P1** | 遗漏高频考点 / 结论不完整 / 格式破坏渲染 | **必须修订** |
| **P2** | 表述不清、优先级排序不合理、篇幅失衡 | 建议修订 |
| **P3** | 措辞、排版细节 | 可忽略或批量优化 |

## 审查任务的分派方式

**推荐组合：按"科目 × 维度"分派，而不是"一个 reviewer 看完一个科目所有维度"。**

对每个科目：

- 该科目 part 数 ≤ 2 且题量 < 100（小科目）→ 派 **2–3 个 reviewer**，覆盖 D1+D2、D3+D4、D5+D6；
- 大科目（如刑法 5 个 part、民法 4 个 part）→ 按维度分派 **5–6 个 reviewer**，D6 单独一个（它需要跨 part 视野）。

单批并行数 7–8 个，与人并行上限一致。40 个单元的规模下，审查批次数 ≈ reviewer 总数 / 8 向上取整。

## 审查报告格式（reviewer 必须遵守）

每个 reviewer 输出一个 Markdown 报告到 `scrape/reviews/<科目>__<维度>.md`，格式固定：

**解析硬约束**（`05_review_aggregate.js` 按此解析）：问题清单表格每行 6 列；严重度列只写 `P0`/`P1`/`P2`/`P3`（不加粗、不带括号）；任何单元格内禁止竖线 `|` 与换行；「结论摘要」的条数必须与表格实际行数一致。

```
# 审查报告：<科目> / <维度编号 维度名>
审查范围：<part 文件列表>
审查时间：<ISO 时间>

## 结论摘要
- P0: n 条, P1: n 条, P2: n 条, P3: n 条

## 问题清单
| # | 严重度 | 位置（part + 知识点标题） | 问题 | 建议改法 | 依据 |
|---|---|---|---|---|---|
| 1 | P0 | 刑法_part2of5 / 共犯形态 | ... | ... | 刑法第25条 |

## 未发现问题说明
（若某方面检查过但没问题，明确写出来，便于判断覆盖率）
```

**注意**：reviewer 只**报告**，不直接改笔记。修订统一由一个独立的修订环节做，避免多人并发改同一文件产生冲突。

## 修订与复审

1. **汇总**：运行 `scripts/05_review_aggregate.js`，把所有报告合并成 `scrape/reviews/_fixlist.md`，按 subject → 严重度排序，并给出每个文件的待修条数。
2. **修订**：对每个「有 P0/P1 的科目」派一个修订 subagent（提示词见 `assets/review_prompt_template.md` 的第二部分）。修订 agent 可以改笔记，但**只能改报告里点到的地方**，不得顺手重写。
3. **复审**：只对 P0 问题做复审 —— 派一个 reviewer 检查修订是否到位、是否引入新错误。P1 及以下抽检即可。
4. **记录**：把最终审查统计写入交付说明（P0 全部修复数、遗留问题），让考生知道这份笔记的可信度边界。
